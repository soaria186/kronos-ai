## #1 · ci: gitleaks, lint y chequeo de R1

- **Tipo:** PR · **Autor:** soarai2026 · **Creado:** 2026-10-06 · **Estado:** closed · **Cerrado:** 2026-10-06
- **Rama:** `feat/e1-ci` → `develop` · **Mezclado:** 2026-10-06 por soarai2026 · 2 commits, 3 archivos (+218 / −0)

## Resumen

- **`.gitattributes`**: normaliza los finales de línea a LF (`* text=auto eol=lf`) y fija LF siempre para `*.sh`, `*.sql`, `*.yml`, `*.yaml` y `Dockerfile`.
- **`.github/workflows/ci.yml`**: se ejecuta en cada pull request hacia `develop` y `main`, con tres jobs:
  - **gitleaks**: escanea todo el historial (`fetch-depth: 0`) con gitleaks v8.30.1, la misma versión que el hook de pre-commit. Descarga el binario y verifica su checksum SHA-256.
  - **ruff**: lint de Python (ruff 0.16.10). Si el repo no tiene archivos `.py`, el job se omite sin fallar.
  - **R1**: ejecuta `tools/check_r1.py`.
- **`tools/check_r1.py`**: falla si algún archivo de `decision/` importa `ejecucion`, `persistencia` o `conectores`. Usa `ast`, no expresiones regulares, y detecta:
  - `import x` y `import x.y`
  - `from x import ...` y `from x.y import ...`
  - imports relativos que suben hasta esos paquetes (`from ..persistencia import y`, `from .. import conectores`)
  - imports dinámicos con nombre literal (`importlib.import_module("x")`, `__import__("x")`)

  También falla si un archivo de `decision/` no se puede analizar.

## Pruebas

- [x] Con un archivo temporal `decision/_prueba_r1.py` que contiene `from persistencia import x`, el chequeo falla (exit 1). Sin el archivo, pasa (exit 0). El archivo de prueba no se commiteó.
- [x] Con una copia fuera del repo se probaron las formas `import`, `from x.y`, relativas y dinámicas. No hubo falsos positivos con `os`, `decision.*`, `from . import ...` ni `persistencia_extra`.

## #25 · feat(validacion): VALIDATE guarda la alerta completa en ALERTA_RECIBIDA

- **Tipo:** PR · **Autor:** soarai2026 · **Creado:** 2026-10-15 · **Estado:** closed · **Cerrado:** 2026-10-16
- **Rama:** `feat/e2-validate-alerta-completa` → `develop` · **Mezclado:** 2026-10-16 por PatricioDU · 3 commits, 7 archivos (+618 / −5)

## Qué resuelve

SOAR-EXECUTE lee `detalle.get("alerta", {})` del evento `ALERTA_RECIBIDA` para sacar el agente (`agent.id`) y el objetivo de la medida (IP, cuenta, servicio, PID). VALIDATE no escribía nada ahí, así que EXECUTE no podía ejecutar nada real. Este PR agrega ese paso.

`validacion/servicio.py` → `registrar(repositorio, tenant_id, alerta_wazuh)`:
- toma una alerta de `alerts.json` que pasó por una regla de sobre (`kronos_fX`; las demás devuelven `None`);
- crea el ticket (`alerta_ref` = `id` de la alerta, título = descripción de la regla sin «Kronos Fx:», severidad = `rule.level`);
- guarda en `ALERTA_RECIBIDA` el detalle `{"alerta": <alerta completa, tal como llegó>}`.

Lo guardado es una **copia de la alerta original**, no el texto recortado que ve el modelo: EXECUTE necesita los valores exactos. El módulo no importa `persistencia` (ni `psycopg`): recibe el repositorio, como EXECUTE, y se prueba con uno falso.

## Dos cosas que encontré al hacerlo

**1. Hueco en la lista de exclusión (`fix`, commit aparte).** EXECUTE interpreta las IP con `ipaddress`, que acepta varias escrituras de la misma dirección (`::ffff:192.0.2.5`, `0:0:0:0:0:ffff:c000:205`, ceros de más en IPv6). `ListaExclusion` comparaba texto: una IP excluida como `192.0.2.5` **no coincidía** con esas formas y EXECUTE habría bloqueado igual. Ahora, en la categoría `ip`, entradas y valores se comparan en su forma canónica. La prueba falla sin el arreglo y pasa con él.

**2. Alertas hostiles.** `alerts.json` se parsea con `json.loads`, que acepta `\^@` y sustitutos UTF-16 sueltos dentro de un string. PostgreSQL no los admite en un `jsonb`, y la bitácora es de solo inserción. Quien controle un campo (un usuario SSH, una línea de comandos) podría hacer que VALIDATE fallara al registrar esa alerta. Antes de guardar se reemplazan por U+FFFD; los números no finitos, las claves que chocan y los valores que no son JSON se rechazan con `AlertaInvalida` **sin tocar la base**.

## Pruebas

- **Unitarias (29 nuevas: 23 de registro y 6 de IP; 227 en total contra 198 en `develop`, todas pasan):** la alerta se guarda completa y como copia; título, severidad y referencia; relectura; alerta sin etiqueta o inválida no llega a la base; alerta hostil; y el contrato con EXECUTE (de lo guardado salen el agente, la IP, la cuenta y el PID).
- **Invariante «EXECUTE solo actúa sobre lo que VALIDATE revisó».** Sobre las 150 alertas de `casos_150`: todo valor sobre el que EXECUTE actuaría, si estuviera en la lista de exclusión, haría que VALIDATE lo detectara (30 órdenes de IP, 31 de cuenta, 5 de servicio, 136 de equipo). Verifiqué que la prueba no es vacía: falla si se desactiva el arreglo de las IP.
- **Integración contra la base real (16-10-2026, SOAR-CORE-01, imagen `kronos-pruebas` en la red `kronos_interna`, `kronos_worker`): `tests/integracion/test_validate_alerta.py`, 3 de 3 pasan.** La alerta vuelve íntegra a EXECUTE tras pasar por `jsonb` y por la cadena de hash; la relectura no duplica el ticket ni el evento; una alerta con `\^@` se registra. Dejaron filas permanentes en la bitácora con inquilinos al azar, como las demás pruebas de integración.
- `ruff check .` y `python tools/check_r1.py` pasan.

**Lo que esa prueba no demuestra:** que `jsonb` *rechace* `\^@` sin la sustitución por U+FFFD; eso sigue viniendo de la documentación de PostgreSQL. Lo que sí demuestra es que, con la sustitución, la alerta hostil se guarda.

## Para decidir (no cambié nada)

- **Tamaño.** No hay tope al tamaño de la alerta guardada. La tabla es inmutable y se conserva 2 años (D-27), así que una alerta anómala muy grande queda para siempre. Hoy lo limita el cortacircuito (30 alertas en 10 minutos), no el tamaño.
- **Datos personales.** La alerta completa puede traer cuentas de usuario, rutas y líneas de comandos, y no se puede borrar de una cadena de solo inserción. Es el mismo problema de R-09 (expirar una cadena inmutable), ahora con más datos dentro.
- Las 150 alertas de prueba no traen `processId`, así que el PID se cubre con una alerta de Sysmon hecha a mano.

## Falta (siguientes PR)

Este PR es solo el registro, que era lo que bloqueaba a EXECUTE. El resto del ciclo (clasificar → validar → `registrar_decision`, contadores, cortacircuito y `python -m validacion`) está en el PR #28.
